## Summary

Phase 8.5 is a **statistical-bucketing analysis** built on top of three settled foundations: the OHLCV cache (Phase 8.4 D-01), the PitClock (Phase 8 D-25 + 8.4 D-03), and the Phase 7 4yr evaluator (`backtest_4yr_evaluate.run_4yr_evaluation`, plus the Daily-swing and M15-scalp paths inside `backtest_hybrid.py`). The phase's novelty is not in algorithms but in **how trades are bucketed** along five orthogonal axes (session × HoD × DoW × DoM × DoY) and in **how recurring high-volatility windows are mined empirically** from the bars table itself rather than from an external feed.

The recommended pipeline: (1) generate trades for every active combo in `pair_config.py` via the Phase 7 evaluator, with the Daily-swing + M15-scalp branches each plugged in at parity; (2) bucket trades by `entry_ts.dt.{hour,dayofweek,day,dayofyear}` and by session-mask; (3) compute Sharpe / win-rate / trade-count per bucket using **trade-count-based annualization** (Sharpe × √N where N = bars-per-year for that timeframe — see §Bucketing Math); (4) materialize per-combo CSVs and seaborn heatmaps with `RdYlGn` diverging colormap centered at 0 and `insufficient_evidence` cells masked to a distinct gray; (5) detect blackout windows by computing rolling 2.5σ z-scores of realized range against same-(hour, dow) 4yr baselines and **clustering detection timestamps into parametric YAML patterns** (e.g., `wom: 1FRI`, `time: 12:30`, `affects: [USD]`); (6) emit a generated `session_config.py` Python literal that `temporal_filters.is_tradeable_session()` and `.is_blackout_window()` import as their data source.

**Primary recommendation:** Reuse `run_4yr_evaluation()` and the `_run_scalp_loop` / `_run_momentum_loop` / `_metrics_from_trades` machinery as the trade source — do **not** fork the evaluator. Add a single new helper `run_full_evaluation_for_temporal(pair, strategy, timeframe)` that dispatches to the right loop (scalp → `_run_scalp_loop`; momentum → `_run_momentum_loop`; m15-scalp → `backtest_hybrid._backtest_m15_symbol`; swing → `backtest_hybrid._backtest_swing_symbol`) and returns a unified trade DataFrame with `entry_ts`, `exit_ts`, `pnl_pct`, and a synthetic `bucket_ts` (= `entry_ts` per D-02 — bar-start ownership) ready for bucketing. This keeps the bucketing layer purely additive on top of Phase 7's PiT-validated trade generation.

### Pattern 1: Vectorized session-mask construction (avoid `.apply`)
**What:** Build per-row boolean masks for each session window using pandas `Series.between()` on `.dt.hour`, then assign a `session` categorical column once.
**When to use:** Initial bucketing pass on every trade DataFrame; the inner loop of bucket aggregation must be vectorized (a 24,000-row 4yr H1 trade history will time out under `.apply`).
**Example:**
```python
# Source: pandas timeseries docs — https://pandas.pydata.org/docs/user_guide/timeseries.html
def assign_session(trades: pd.DataFrame) -> pd.DataFrame:
    """Per D-01/D-02: tag each trade by entry_ts hour-of-day → session.
    Bar at 06:55 belongs to no session; bar at 07:00 belongs to London (and London-open).
    """
    h = trades["entry_ts"].dt.hour  # tz-aware UTC by D-01
    trades = trades.copy()
    # Primary session (mutually exclusive: Tokyo / London / NY / OFF)
    trades["session"] = "OFF"
    trades.loc[h.between(0, 8, inclusive="left"),  "session"] = "TOKYO"   # 00:00-09:00
    trades.loc[h.between(7, 15, inclusive="left"), "session"] = "LONDON"  # 07:00-16:00 (overrides Tokyo overlap 07-09)
    trades.loc[h.between(13, 21, inclusive="left"), "session"] = "NY"    # 13:00-22:00 (overrides London overlap 13-16)
    # Auxiliary flags (non-mutually-exclusive — bucketed independently)
    trades["in_overlap"]      = h.between(13, 15, inclusive="left")  # 13:00-16:00
    trades["in_london_open"]  = h.between(7,  8,  inclusive="left")  # 07:00-09:00
    return trades
```
**Why:** `.between()` is C-vectorized; `.apply(lambda r: _session(r.hour))` is row-iterated Python and 200×–500× slower. The existing `backtest_hybrid._session()` helper (line 47-50) is already the pattern — extract it and extend.

### Pattern 3: Heatmap matrix with masked `insufficient_evidence` cells
**What:** A 2D `(pair, hour)` or `(pair, dow)` matrix as a single seaborn heatmap per strategy × timeframe, with per-cell numeric annotation and gray cells where `trade_count < 30`.
**When to use:** SESS-02 outputs. One PNG per `(strategy, timeframe, bucket_dim)` covering all pairs.

```python
# Source: seaborn 0.13.2 docs — https://seaborn.pydata.org/generated/seaborn.heatmap.html
import seaborn as sns
import matplotlib.pyplot as plt
import numpy as np

def render_heatmap(matrix: pd.DataFrame, counts: pd.DataFrame, title: str, out_path: Path):
    """matrix: rows=pair, cols=hour-of-day (0-23), values=Sharpe.
    counts: same shape, values=trade_count. Cells where counts<30 → masked → gray.
    """
    mask = counts < 30
    fig, ax = plt.subplots(figsize=(14, max(4, 0.6 * len(matrix))))
    sns.heatmap(
        matrix,
        cmap="RdYlGn",      # diverging — red negative, yellow ~zero, green positive
        center=0,           # critical: anchors the zero-Sharpe color
        vmin=-1.0, vmax=1.0,  # clip extreme outliers (rare bucket Sharpe > 1 dominates colormap otherwise)
        annot=True, fmt=".2f",
        mask=mask,           # gray cells = insufficient_evidence
        cbar_kws={"label": "Sharpe (annualized)"},
        ax=ax,
    )
    ax.set_title(title)
    fig.tight_layout()
    fig.savefig(out_path, dpi=120)
    plt.close(fig)
```
**Why:** `mask=` is the standard seaborn idiom for "don't render this cell" — beats zero-fill (which lies green/yellow) and beats dropping (which silently shifts column alignment). `center=0` + `RdYlGn` is the de facto Sharpe-heatmap convention.

### Pattern 4: Trade-count-based Sharpe annualization (per timeframe per session-bucket)
**What:** Annualize per-bucket Sharpe using the **bar count** for that timeframe × bucket, not blanket √252.
**When to use:** `_compute_bucket_metrics(bucket_trades, timeframe)` — every metric row in every CSV.
**Example:**
```python
# Standard finance practice — sigma scales by sqrt(time)
# Source: https://en.wikipedia.org/wiki/Sharpe_ratio
ANNUALIZATION_BARS_PER_YEAR = {
    "Daily": 252,           # 252 trading days
    "H1":    252 * 24,      # 6048 H1 bars (forex 24h, 5 days/wk → 24*5*52 ≈ 6240; use 6048 conservative)
    "M15":   252 * 24 * 4,  # 24192 M15 bars
    "H4":    252 * 6,       # 1512 H4 bars (not used in 8.5 strategy analysis but used in blackout detection)
}
def annualization_factor(timeframe: str) -> float:
    return float(ANNUALIZATION_BARS_PER_YEAR[timeframe]) ** 0.5

def bucket_sharpe(pnl: pd.Series, timeframe: str) -> float:
    """Per-trade pnl_pct → annualized Sharpe.
    Phase 7 used sqrt(252) for H1 — that's a known under-annualization, but
    the routing-matrix decisioning is consistent across all 8 pairs so the
    relative ranking is preserved. Phase 8.5 follows the SAME convention to
    avoid mixing two Sharpe conventions in one report; if any plan switches
    convention, document the override and recompute the Phase 7 numbers too.
    """
    if pnl.std() == 0 or len(pnl) == 0:
        return 0.0
    return float(pnl.mean() / pnl.std() * np.sqrt(252))   # match Phase 7
```
**Decision (locked):** **Use Phase 7's √252 convention** to match the established routing matrix. The constants table above is documented for reference but **not used in v1** — switching annualization conventions across phases would invalidate every downstream comparison against `pair_config.py` notes.

**Why:** The Phase 7 evaluator computes `pnl.mean() / pnl.std() * np.sqrt(252)` regardless of whether trades were sourced from H1, M15, or Daily bars (line 238). This is technically an under-annualization for intraday data, but **the threshold gates (Sharpe ≥ 0.5 in Phase 7, Sharpe ≥ 0.3 in 8.5) are calibrated to that convention.** Mixing conventions would mean a 0.3 bucket Sharpe in 8.5 is actually higher quality than a 0.5 strategy Sharpe in Phase 7, which violates intuition. **Stay consistent.**

### Pattern 5: Empirical risk-calendar pipeline (detect → cluster → parameterize)
**What:** Three-stage pipeline that turns "spike timestamps" into reusable patterns.
**When to use:** SESS-03 only — produces `risk_calendar.yaml`.
**Stages:**

**Stage A — Detect anomaly bars (per pair × timeframe):**
```python
def detect_blackout_bars(bars: pd.DataFrame, sigma: float = 2.5) -> pd.DatetimeIndex:
    """Per D-10: realized range > 2.5σ above same-(hour, dow) baseline.

    Spread proxy when bars.spread is null: use (High - Low) / Close as a
    realized-volatility proxy. Computed per-bar; baseline computed over the
    full 4yr corpus grouped by (hour, dow).
    """
    bars = bars.copy()
    bars["range_pct"] = (bars["High"] - bars["Low"]) / bars["Close"]
    bars["hour"] = bars.index.hour
    bars["dow"]  = bars.index.dayofweek

    # Baseline: per-(hour, dow) mean and std over the full 4yr window
    baseline = bars.groupby(["hour", "dow"])["range_pct"].agg(["mean", "std"])
    bars = bars.join(baseline, on=["hour", "dow"], rsuffix="_baseline")
    z = (bars["range_pct"] - bars["mean"]) / bars["std"]

    return bars.index[z > sigma]
```
*Note on rolling vs full-window baseline:* CONTEXT.md D-10 specifies "same (hour-of-day, day-of-week) 4yr baseline" — **full-window** baseline is correct (not rolling). Rolling would smear NFP into its own baseline and miss it. Full-window is the standard event-study baseline.

**Stage B — Cluster timestamps into recurring patterns:**
```python
def cluster_into_patterns(stamps: pd.DatetimeIndex) -> list[dict]:
    """Group spike timestamps into parametric patterns.

    Pattern recognizers (apply in order; first match wins):
      1. wom-N-DDD  (Nth weekday-of-month) — e.g., 1st Friday of every month at HH:MM
      2. dow-DDD    (every weekday at HH:MM) — e.g., every Wednesday 18:00 UTC (FOMC presser)
      3. mom-DD     (Nth day of every month) — e.g., 15th of every month
      4. yearly-MM-DD — annual single-date events (Christmas thin liquidity)
      5. unrecognized — emit as raw timestamp list with `pattern: oneoff`
    """
    # Group by (hour, minute) — events recur at fixed UTC times
    by_time = stamps.groupby([stamps.hour, stamps.minute])
    patterns = []
    for (hh, mm), group in by_time:
        # Test wom-N-DDD: are all timestamps the Nth occurrence of weekday W in their month?
        if _matches_wom(group):
            n, dow = _extract_wom(group)
            patterns.append({"pattern": "wom", "n": n, "dow": dow,
                             "time": f"{hh:02d}:{mm:02d}", "duration_min": 30,
                             "evidence_count": len(group)})
        # ... else try other patterns ...
    return patterns
```

from datetime import datetime, timedelta
from .session_config import SESSION_RULES, BLACKOUT_PATTERNS

def is_tradeable_session(pair: str, strategy: str, timeframe: str, ts: datetime) -> bool:
    """Hard veto. False blocks entry. (D-06)"""
    rule = SESSION_RULES.get((pair, strategy, timeframe))
    if rule is None:
        return True   # no analysis = permit (let other gates decide)
    if ts.hour in rule.get("blacklisted_hours", []):
        return False
    if ts.weekday() in rule.get("blacklisted_dows", []):
        return False
    # Currency-scoped blackout check (per D-13)
    if not _passes_blackout_check(pair, ts):
        return False
    return True

def is_blackout_window(ts: datetime) -> bool:
    """Global ts-only filter. (D-07)"""
    for pattern in BLACKOUT_PATTERNS:
        if _matches_pattern(pattern, ts):
            return True
    return False

### Anti-Patterns to Avoid
- **`.apply(lambda)` for session bucketing on a 24k-row DataFrame:** 200×–500× slower than vectorized `.between()`. Use Pattern 1.
- **Forking `_run_scalp_loop` to "tweak it for bucketing":** the loop is already PiT-safe and BKTS-01-corrected. Wrap with a dispatcher (Pattern 2), don't copy-paste.
- **Hardcoding the 13-combo matrix as a tuple literal in `temporal_analysis.py`:** the active matrix is whatever `pair_config.PAIR_CONFIGS[pair].allow_*` says today. Iterate at runtime.
- **Reading 4yr CSVs via `pd.read_csv("V2/data/USDJPY_H1_4yr.csv")` directly:** violates D-17. All bar reads go through `cache.get_bars()` inside `with PitClock(end_ts):`. The CSVs exist on disk but the cache is the canonical source.
- **PyYAML for `risk_calendar.yaml`:** drops comments and reorders keys → operator manual entries silently mutate. Use ruamel.yaml.
- **Zero-filling `insufficient_evidence` cells in heatmaps:** lies — a gray-masked cell tells the operator "not enough data"; a yellow cell tells them "neutral Sharpe". Use Pattern 3's `mask=`.
- **Annualizing per-bucket Sharpe with a different factor than Phase 7:** breaks comparability with `pair_config.py` notes. Stay √252 across the project until a documented migration phase says otherwise.
- **Detecting blackouts on a rolling baseline:** smears recurring events into their own baseline. Use full 4yr (hour, dow) baseline per D-10.

## Common Pitfalls

### Pitfall 1: Trade-overlap session ownership ambiguity
**What goes wrong:** A trade enters in London (08:00 UTC) and exits in NY (15:00 UTC). Which session "owns" this trade for bucketing — does it count toward London's Sharpe or NY's, or both?
**Why it happens:** D-02 specifies bar-start ownership at the bar level, but a *trade* is a multi-bar object with an entry_ts and exit_ts.
**How to avoid:** **Bucket by `entry_ts` only** (matches D-02's intent — a trade is "owned" by the session in which the entry signal fired). Document this explicitly in `temporal_analysis.py` docstring. Do NOT double-count by exit-session; do NOT split pnl pro-rata across sessions (that's a router-policy concern for Phase 9, not a per-bucket-statistic concern).
**Warning signs:** Trade-count totals across sessions don't equal the total trade count → you're double-counting via exit_ts. Sum check on every CSV: `sum(per_session.trade_count) == total trade count`.

### Pitfall 2: M15 60d → 4yr — DoM/DoY bucketing thinness
**What goes wrong:** Even with the new 4yr M15 corpus (Phase 8.4 P03), DoM/DoY buckets for M15 are ~12 trades per (pair, strategy, M15, day) on average — way below D-03's 30-trade gate.
**Why it happens:** ~24k 15-min bars/year × 4yr / (28 days × 12 months × 8 pairs × 4 strategies) ≈ low double-digit trade-count per DoM bucket per combo. DoY is even thinner.
**How to avoid:** Per CONTEXT.md D-14 — **DoM and DoY heatmaps are H1 + Daily only**. M15 emits HoD + DoW only. The CSV row still exists for thin M15 DoM/DoY buckets but with `status: insufficient_evidence`. Plan task should explicitly skip the M15 DoM/DoY heatmap render path.
**Warning signs:** A M15 DoY heatmap renders mostly gray — confirmed thin; don't fight it, just don't render it.

### Pitfall 3: DST illusion at month boundaries
**What goes wrong:** "We said no DST adjustment, so why does my London-session bar at the last Sunday of October have weird Sharpe?"
**Why it happens:** IC Markets MT5 server time is GMT+0 in winter and GMT+0 in summer (per Phase 8.4 D-02). But broker rollover at 22:00 UTC on Friday and Sunday-evening reopen are slightly shifted in DST seasons. The bars are UTC, but the Sunday-evening reopen and Friday-close patterns shift by 1 hour twice a year.
**How to avoid:** Tag bars within ±2 hours of Sunday 22:00 UTC and Friday 22:00 UTC with a `near_market_boundary` flag. Don't drop them — but allow the operator to filter in heatmaps if the noise is ugly. **Default behavior:** include all bars; document in `summary.md` that two ~1-hour shoulders per year are noisy due to DST-driven liquidity changes (NOT due to timezone math, which is correct).
**Warning signs:** Two thin spikes in the DoY heatmap around the last Sundays of March and October — that's DST-driven liquidity, not analysis bug.

### Pitfall 4: Spread-proxy sensitivity (when `bars.spread` is null)
**What goes wrong:** `bars` table from Phase 8.4 D-02 has no `spread` column — only OHLCV. Risk-calendar detection needs a spread proxy, but `(High - Low) / Close` proxies are noisy at low-liquidity hours (Tokyo midnight) where range is small for benign reasons.
**Why it happens:** The 2.5σ z-score is computed against the same-(hour, dow) baseline, so low-liquidity baselines have low std → spurious detections during otherwise-normal Tokyo hours.
**How to avoid:** Add a **floor on baseline std**: if `std < 1e-5`, skip that (hour, dow) cell — emit no detections from low-liquidity baselines. Document the floor in `risk_calendar.yaml` header comment.
**Warning signs:** Detected blackouts cluster at 23:00-04:00 UTC for weekday pairs → false positives from thin Tokyo baselines.

### Pitfall 5: PitClock context-manager exhaustion
**What goes wrong:** Inner-loop bucketing reads bars repeatedly; nesting a fresh `with PitClock(end_ts):` for each `(pair, strategy, timeframe)` combo bumps the depth counter 13 times.
**Why it happens:** `pit.py:_PIT_THREAD_DEPTH` is thread-local — fine for sequential code, but a top-level `with PitClock(end_ts):` wrapping the whole batch run is enough.
**How to avoid:** Wrap the **entire** `run_temporal_analysis.main()` in a single `with PitClock(end_ts):` block. Inner functions can call `cache.get_bars()` freely; the depth stays at 1 throughout. Don't nest.
**Warning signs:** `cache.is_pit_active()` returns True even after the analysis run completes → balanced enter/exit got out of sync (likely an exception swallowed inside a nested with-block).

### Example 2: Per-bucket metrics (vectorized groupby)
```python
# Source: this RESEARCH.md §Pattern 1 + §Pattern 4 — reuses Phase 7 _metrics_from_trades convention
def bucket_trades(trades: pd.DataFrame, timeframe: str) -> dict[str, pd.DataFrame]:
    """Return {dimension_name: DataFrame} for each bucket axis.

    Dimensions: session, hour, dow (always); dom, doy (H1+Daily only per D-14).
    Each DataFrame has columns: bucket, sharpe, win_rate, trade_count, status.
    """
    trades = ta.assign_session(trades)              # Pattern 1
    trades["hour"] = trades["entry_ts"].dt.hour
    trades["dow"]  = trades["entry_ts"].dt.dayofweek
    trades["dom"]  = trades["entry_ts"].dt.day
    trades["doy"]  = trades["entry_ts"].dt.dayofyear

    out = {}
    dims = ["session", "hour", "dow"]
    if timeframe in ("H1", "Daily"):
        dims += ["dom", "doy"]

    for dim in dims:
        agg = trades.groupby(dim).agg(
            sharpe=("pnl_pct", lambda s: float(s.mean() / s.std() * (252**0.5))
                                          if s.std() > 0 else 0.0),
            win_rate=("pnl_pct", lambda s: float((s > 0).mean())),
            trade_count=("pnl_pct", "count"),
        )
        agg["status"] = agg["trade_count"].apply(
            lambda n: "insufficient_evidence" if n < 30
                      else "good" if agg.loc[agg.index, "sharpe"] >= 0.3
                      else "bad"  if agg.loc[agg.index, "sharpe"] <= -0.2
                      else "neutral"
        )
        out[dim] = agg.reset_index()
    return out
```

def render_combo_heatmaps(buckets: dict, pair: str, strategy: str,

### Example 5: Predicate API in `temporal_filters.py`
```python
# Source: this RESEARCH.md §Pattern 6
from datetime import datetime
from .session_config import SESSION_RULES, BLACKOUT_PATTERNS

# Currency-pair extraction (USDJPY → ["USD", "JPY"])
def _pair_currencies(pair: str) -> list[str]:
    return [pair[:3], pair[3:]]

def is_tradeable_session(pair: str, strategy: str, timeframe: str,
                          ts: datetime) -> bool:
    """D-06: hard veto. False blocks entry; True permits (other gates may still reject)."""
    rule = SESSION_RULES.get((pair, strategy, timeframe))
    if rule is not None:
        if ts.hour    in rule.get("blacklisted_hours", []): return False
        if ts.weekday() in rule.get("blacklisted_dows",  []): return False
    # Currency-scoped blackout (D-13)
    affected = set(_pair_currencies(pair))
    for pattern in BLACKOUT_PATTERNS:
        if affected.intersection(pattern["affects"]) and _matches_pattern(pattern, ts):
            return False
    return True

def is_blackout_window(ts: datetime) -> bool:
    """D-07: global ts-only filter (currency-agnostic blanket gate)."""
    return any(_matches_pattern(p, ts) for p in BLACKOUT_PATTERNS)

def _matches_pattern(pattern: dict, ts: datetime) -> bool:
    """Resolve a parametric pattern against a concrete ts. ts assumed UTC (D-01)."""
    if pattern["pattern"] == "wom":
        nth_dow = (ts.day - 1) // 7 + 1   # 1st/2nd/3rd/4th occurrence of weekday
        if nth_dow != pattern["n"]: return False
        if ts.weekday() != pattern["dow"]: return False
        # Within window?
        hh, mm = pattern["time_utc"]
        start = ts.replace(hour=hh, minute=mm, second=0, microsecond=0)
        end   = start + pd.Timedelta(minutes=pattern["duration_min"])
        return start <= ts < end
    # ... handle "dow", "mom", "yearly", "dates" pattern types ...
    return False
```
