## Area 1: OHLCV cache backing store

### Q1.1 — Where does the OHLCV cache live?

| Option | Description | Selected |
|--------|-------------|----------|
| Supabase Postgres (Recommended) | MCP server provisioned. Postgres `bars` table with composite PK. Cross-machine portable, SQL-queryable. ~50ms network roundtrip. | ✓ |
| Local DuckDB | Single .duckdb file. Columnar, fast for analytical scans. Tied to dev host. | |
| Local SQLite | Extend marketmind.db with bars table. One DB file. Slower scans than DuckDB. | |
| Parquet partitioned dir | V2/data/cache/{pair}/{timeframe}.parquet. No DB engine. Dedup in Python. | |

**User's choice:** Supabase Postgres (Recommended).
**Notes:** Aligns with the architectural-audit recommendation; MCP already provisioned reduces integration cost.

### Q1.2 — Cache table structure?

| Option | Description | Selected |
|--------|-------------|----------|
| Single bars table (Recommended) | bars(pair, timeframe, ts, ohlcv, source) with composite PK. Simplest. | ✓ |
| Per-timeframe tables | bars_m15, bars_h1, bars_d1. Narrower scans, 3x DDL overhead. | |
| Per pair×timeframe tables | 24 tables. Fastest narrow lookups, high admin overhead. | |

**User's choice:** Single bars table (Recommended).
**Notes:** Schema simplicity wins; PK composite handles all dedup needs.

### Q1.3 — How do existing callers get bars from the cache?

| Option | Description | Selected |
|--------|-------------|----------|
| Replace CSV reads with cache.get_bars (Recommended) | Existing pd.read_csv calls migrate. Title-case OHLC preserved. Single source of truth. | ✓ |
| Cache writes CSV as side effect | Cache fetches and writes CSVs; existing readers unchanged. Two sources of truth. | |
| Both: API + CSV mirror | Maximum back-compat, double-write cost. | |

**User's choice:** Replace CSV reads with cache.get_bars (Recommended).
**Notes:** Closes the "two sources of truth" risk surface from the audit.

### Q1.4 — When does the cache pull new bars from the broker?

| Option | Description | Selected |
|--------|-------------|----------|
| On-demand auto-pull on read (Recommended) | get_bars() detects gap, pulls (max_ts, now], INSERT ON CONFLICT DO NOTHING. | |
| Manual CLI step | Operator runs update_cache CLI before reading. Deterministic. | |
| Both: manual CLI + on-demand fallback | CLI for batch pre-warm, on-demand fallback. | ✓ |

**User's choice:** Both: manual CLI + on-demand fallback.
**Notes:** User chose maximum operator control over pure-recommendation. Manual CLI for predictable batch runs; on-demand for ad-hoc.
