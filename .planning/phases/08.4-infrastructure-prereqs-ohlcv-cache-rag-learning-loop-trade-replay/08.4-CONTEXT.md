**Gathered:** 2026-04-25

<domain>
## Phase Boundary

Close five infrastructure gaps surfaced in the 2026-04-25 architectural audit so Phase 8.5's heavy temporal analysis runs on stable foundations:

1. **OHLCV cache layer** (Supabase Postgres) replacing ad-hoc CSV-on-disk with incremental delta fetch
2. **GBPNZD H1 4yr data parity** + 4yr routing-matrix re-evaluation (PiT-gated)
3. **H4 timeframe data provisioning** for all 8 pairs (data only — H4 strategies are NOT in scope)
4. **RAG learning loop closure** (per-trade hook → SQLite trades + decision_log + ChromaDB)
5. **Trade-replay MQ5 indicator** + ADR helper + ADR levels indicator (must render on all timeframes)
6. **mempalace** configured properly as a secondary structured-knowledge store

Strategy router, S&R / pivots / fibonacci, walk-forward retraining, and live engine wiring are out of scope (Phase 9, possible Phase 8.6, v3.0 EXPN-03, Phase 10 respectively).

<decisions>
## Implementation Decisions

### OHLCV Cache (INFRA-01)
- **D-01:** Backing store is **Supabase Postgres** via the project's existing MCP server (mcp__supabase__*). Survives dev-host wipes; cross-machine portable; SQL-queryable for ad-hoc analysis. Network roundtrip ~50ms acceptable for batch backtest reads.
- **D-02:** **Single `bars` table**, schema: `bars(pair TEXT, timeframe TEXT, ts TIMESTAMPTZ, open NUMERIC, high NUMERIC, low NUMERIC, close NUMERIC, volume NUMERIC, source TEXT, PRIMARY KEY (pair, timeframe, ts))`. Source column tags provenance ('MT5', 'yfinance', 'Dukascopy-historical'). Covers all 8 pairs × 4 timeframes (M15/H1/H4/Daily) in one place.
- **D-03:** Read API: `cache.get_bars(pair, timeframe, start, end) -> pd.DataFrame` returning Title-case OHLC columns (Open, High, Low, Close, Volume — matches existing CSV column convention). Replaces existing `pd.read_csv` callers across V2/backtest/, V2/v3_intelligence/, V2/scripts/. Single source of truth.
- **D-04:** Fetch trigger is **dual-mode**: (a) manual CLI `python -m scripts.update_cache --pair X --tf Y --since auto` for batch pre-warming, (b) on-demand auto-pull when `cache.get_bars()` finds the requested range exceeds `max(ts)` for that (pair, timeframe) — pulls (max_ts, now] from broker and `INSERT ... ON CONFLICT DO NOTHING`.

### GBPNZD H1 4yr Data Parity (INFRA-02)
- **D-05:** Primary fetch path is **MT5 GUI export** (matches the provenance of the other 7 pairs per Phase 7 D-15). Fallback chain mirrors download_history.py header: A (MT5 GUI) → B (Wine Python) → D (Dukascopy historical ticks aggregated to H1). Note: Dukascopy as historical-only backfill is distinct from the REQUIREMENTS.md line 70 ban on Dukascopy as a *live feed*.
- **D-06:** Fetched data lands in **both** locations: `V2/data/GBPNZD_H1_4yr.csv` (parity with the other 7 pairs' on-disk artifacts) AND the Supabase `bars` table. CSV is operator-readable provenance; Supabase is the analytical source.
- **D-07:** After fetch, **re-run the Phase 7 4yr scalp/momentum/swing evaluator on GBPNZD**, PiT-gated. If any strategy crosses positive Sharpe at the established Phase 7 threshold, update [pair_config.py](../../V2/v3_intelligence/pair_config.py) with new GBPNZD entries. Otherwise keep current (M15-only). This is data parity AND matrix parity, not data alone.

### H4 Timeframe Provisioning
- **D-08:** **H4 data is fetched in Phase 8.4** for all 8 pairs over a 4yr window (~8 MT5 GUI exports), persisted to CSVs `V2/data/{PAIR}_H4_4yr.csv` and inserted into the Supabase `bars` table. Operator instruction 2026-04-25.
- **D-09:** **H4 strategy implementation is OUT OF SCOPE** for Phase 8.4 — only data infrastructure is provisioned. Cache schema accepts arbitrary timeframe strings; H4 is a first-class citizen alongside M15/H1/Daily. Trade-replay and ADR indicators must compile and render on H4 charts even though no H4 strategies exist yet. H4 strategy development belongs in a future phase once routing-matrix evidence is gathered.

### RAG Learning Loop Closure (INFRA-03)
- **D-10:** Single entry point: `V2/v3_intelligence/learning_loop.py::on_trade_close(trade: dict) -> None`. Synchronously: (a) writes trade to marketmind.db `trades` table via existing TradeLogger, (b) computes a decision_log diff if strategy params changed since the last trade for that (pair, strategy), (c) embeds the trade into ChromaDB `trade_memory` collection via existing rag_signal_filter helpers.
- **D-11:** **Trigger surface is dual**: per-trade in the backtest harness (called on every closed trade in [backtest_hybrid.py](../../V2/backtest/backtest_hybrid.py) and the Phase 7 4yr evaluator replay loops) AND per-fill in the live engine fill-handler (Phase 10 wires this — Phase 8.4 ships the API and the integration point). Backtest unit tests cover the per-trade path; live integration is verified in Phase 10.
- **D-12:** **Decision_log granularity covers both per-trade snapshots AND pair_config edits.** Per-trade rows capture the active strategy params at entry (z-threshold, ATR multipliers, size_mult, regime label, session, hour-of-day) — one row per closed trade. Pair_config-edit rows capture operator-level routing changes (e.g., "GBPJPY scalp enabled 2026-04-25 after 4yr matrix"). Phase-level architectural notes are NOT logged to DB (covered by CONTEXT.md/STATE.md instead).
- **D-13:** **Embed every closed trade** into ChromaDB `trade_memory`. ChromaDB local handles 10k+ documents comfortably; embeddings are cheap. Aligns with rag_signal_filter.py docstring intent. No downsampling.
- **D-14:** **One-shot backfill** of existing marketmind.db trades is included in Phase 8.4: `V2/scripts/backfill_rag.py` reads existing `trades` rows, embeds each into ChromaDB. Idempotent (skip if doc_id present). Populates RAG immediately rather than waiting for new trades.

### Trade-Replay Indicator + ADR (INFRA-04)
- **D-15:** `V2/indicators/BandD_TradeReplay.mq5` renders **standard scope**: entry arrow, exit arrow, connecting line, SL rectangle, TP rectangle, R-multiple text label per trade (e.g., "1.8R", "-0.7R"). No regime tint, no session ribbon (those belong to dedicated indicators if needed later).
- **D-16:** **All MQ5 indicators built in this phase (and project-wide) MUST render correctly on all four timeframes (M15, H1, H4, Daily).** Operator instruction 2026-04-25 — captured here as a project-level invariant. Test plan includes loading each new indicator on every timeframe in the IC Markets MT5 terminal under Wine.
- **D-17:** **Trade-replay input format is CSV**. Backtest writes `V2/reports/trades_<run-id>.csv` with columns: `entry_ts, exit_ts, entry_px, exit_px, sl, tp, direction, strategy, pair, timeframe`. MQL5 indicator reads via FileOpen with CSV_ANSI flag. Path is configurable via indicator input parameter.
- **D-18:** `V2/v3_intelligence/adr.py` exposes `compute_adr(pair: str, timeframe: str, lookback_days: int = 20) -> float`. Implementation: load Daily bars from cache for pair, mean of `(high - low)` over lookback_days, return as price units. Used by future temporal/risk modules and the ADR levels indicator.
- **D-19:** `V2/indicators/ADR_Levels.mq5` draws three horizontal lines: ADR-high (today's open + ADR/2), ADR-low (today's open − ADR/2), ADR-50% (today's open). Recomputes on bar-close. Compatible with all four timeframes per D-16.

### mempalace Secondary Memory Store

Approach: review [mempalace.yaml](../../mempalace.yaml) room schema, populate keywords with project-relevant terms (regime, RAG, pair_config, session, timeframe, strategy, backtest, MT5, ZMQ, etc.), regenerate entities.json with relevant project entities, and document its role in PROJECT.md so future sessions know which memory layer holds what. claude-mem remains canonical for cross-session conversation memory; mempalace becomes the structured-knowledge store. Operator-chosen approach 2026-04-25 (rejected the "delete + .gitignore" recommendation).
