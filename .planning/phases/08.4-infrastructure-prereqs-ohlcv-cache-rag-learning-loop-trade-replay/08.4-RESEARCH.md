# Phase 8.4: Infrastructure Prereqs — Research

**Researched:** 2026-04-25
**Domain:** Multi-domain — Postgres/Supabase data layer, ChromaDB, MQL5 charting, mempalace tooling
**Confidence:** HIGH for cache + RAG + MQL5 + mempalace; MEDIUM for IC Markets H4 history depth (broker-specific, unverifiable from this Linux dev host)

## Summary

Phase 8.4 closes six infrastructure gaps before Phase 8.5's heavy temporal analysis. The architecture is mostly already decided (CONTEXT.md captures 21 locked decisions); this research answers HOW to implement each one safely.

The riskiest area is **the cache↔PiT interaction (Area 3)** — auto-pulling new bars inside a `PitClock` context would silently leak the future. The recommended fix is a `pit_active` runtime check that downgrades auto-pull to a `FutureBarReadError` whenever a clock is on the call stack. The second-riskiest is **mempalace D-20** — mempalace is a real, installed Python tool with 19 MCP commands, but it is OWNED by user-global config (`~/.mempalace/`), NOT by the repo's `mempalace.yaml`/`entities.json` files. Those two files in the repo are stale auto-detect artifacts the tool produced once and never re-uses. D-20 needs a one-step revision: keep `mempalace.yaml`/`entities.json` for documentation purposes, but the *actual* configuration work runs `mempalace init` + `mempalace mine` against the repo and writes into the user-global palace.

Everything else is well-trodden ground: supabase-py 2.x or psycopg 3.x both work, Postgres composite PKs are stable syntax, ChromaDB upsert is idempotent by design, MQL5 indicators use `Period()` / `_Symbol` / `iTime` to be timeframe-agnostic.

**Primary recommendation:** Use **psycopg 3.3.x** (synchronous) as the in-Python Postgres client (not supabase-py — we don't need RLS/auth/storage, just SQL). Use the **Session pooler** connection string (port 5432 IPv6, port 6543 IPv4 transaction-mode) sourced from `os.environ["SUPABASE_DB_URL"]` loaded via `python-dotenv` from `.env`. Schema migration via `mcp__supabase__apply_migration` (operator-side, agentic) with `CREATE TABLE IF NOT EXISTS`. **Forex prices in `NUMERIC(12,5)`**, JPY pairs implicitly absorbed by scale=5 with leading zeros — single column type, not per-pair branching. Wrap all live-engine + backtest calls in a thin `OHLCVCache` class that exposes `.get_bars(pair, tf, start, end)` returning Title-case OHLC. Auto-pull is gated by a global `is_pit_active()` check.

### Pattern 1: OHLCVCache class (Area 1, 3, 4)

**What:** A thin Python wrapper around psycopg 3 with PiT-aware auto-pull.
**When to use:** Every backtest, evaluator, and (Phase 10) live engine bar read.

```python
# V2/v3_intelligence/cache.py
"""OHLCV cache — Supabase Postgres backing, Title-case OHLC, PiT-safe auto-pull.

Per Phase 8.4 CONTEXT.md decisions:
  D-01: Supabase Postgres backing
  D-02: bars(pair, timeframe, ts, open, high, low, close, volume, source)
  D-03: Title-case OHLC columns returned
  D-04: dual-mode fetch (manual CLI + on-demand auto-pull)
  Phase 8 D-25: PitClock-active calls never auto-pull (would leak future)
"""
from __future__ import annotations
import os
from datetime import datetime
from pathlib import Path
from typing import Optional
import threading

import pandas as pd
import psycopg
from psycopg.rows import dict_row
from dotenv import load_dotenv

load_dotenv(Path(__file__).resolve().parents[2] / ".env")

_DB_URL = os.environ.get("SUPABASE_DB_URL")  # postgresql://...pooler.supabase.com:5432/postgres
_PIT_DEPTH = threading.local()


def is_pit_active() -> bool:
    """True iff caller is inside a PitClock with-block on this thread."""
    return getattr(_PIT_DEPTH, "depth", 0) > 0


class OHLCVCache:
    """Read-through OHLCV cache backed by Supabase Postgres."""

    def __init__(self, db_url: Optional[str] = None) -> None:
        self._db_url = db_url or _DB_URL
        if not self._db_url:
            raise RuntimeError(
                "SUPABASE_DB_URL not set — add it to V2/.env "
                "(get it from Supabase dashboard → Connect → Session pooler)"
            )

    def _connect(self) -> psycopg.Connection:
        # prepare_threshold=None disables prepared statements for pgbouncer/pooler compatibility
        return psycopg.connect(self._db_url, prepare_threshold=None)

    def get_bars(
        self,
        pair: str,
        timeframe: str,
        start: pd.Timestamp,
        end: pd.Timestamp,
    ) -> pd.DataFrame:
        """Fetch bars in [start, end] inclusive. Returns Title-case OHLC.

        If end exceeds max(ts) for this (pair, timeframe) AND we are NOT inside
        a PitClock context, attempt to auto-pull (max_ts, end] from broker.
        Inside a PitClock context, missing bars raise FutureBarReadError.
        """
        with self._connect() as conn, conn.cursor(row_factory=dict_row) as cur:
            cur.execute(
                """
                SELECT ts, open, high, low, close, volume
                FROM bars
                WHERE pair = %s AND timeframe = %s
                  AND ts BETWEEN %s AND %s
                ORDER BY ts ASC
                """,
                (pair, timeframe, start, end),
            )
            rows = cur.fetchall()

            cur.execute(
                "SELECT MAX(ts) AS max_ts FROM bars WHERE pair=%s AND timeframe=%s",
                (pair, timeframe),
            )
            max_ts = cur.fetchone()["max_ts"]

        if max_ts is None or end > max_ts:
            if is_pit_active():
                from .pit import FutureBarReadError
                raise FutureBarReadError(
                    f"Cache requested {pair} {timeframe} up to {end} but cache "
                    f"max_ts={max_ts}; PiT-active so refusing to auto-pull"
                )
            self._auto_pull(pair, timeframe, since=max_ts, until=end)
            return self.get_bars(pair, timeframe, start, end)  # one retry

        df = pd.DataFrame(rows)
        if df.empty:
            return df
        df["ts"] = pd.to_datetime(df["ts"])
        df = df.set_index("ts")
        df = df.rename(columns={"open": "Open", "high": "High",
                                 "low": "Low", "close": "Close", "volume": "Volume"})
        return df

    def upsert_bars(
        self,
        pair: str,
        timeframe: str,
        df: pd.DataFrame,
        source: str,
    ) -> int:
        """Insert bars; on (pair, timeframe, ts) conflict do nothing. Returns rows inserted."""
        records = [
            (pair, timeframe, ts, row["Open"], row["High"], row["Low"],
             row["Close"], row.get("Volume", 0), source)
            for ts, row in df.iterrows()
        ]
        with self._connect() as conn, conn.cursor() as cur:
            cur.executemany(
                """
                INSERT INTO bars (pair, timeframe, ts, open, high, low, close, volume, source)
                VALUES (%s, %s, %s, %s, %s, %s, %s, %s, %s)
                ON CONFLICT (pair, timeframe, ts) DO NOTHING
                """,
                records,
            )
            inserted = cur.rowcount
            conn.commit()
        return inserted

    def _auto_pull(
        self,
        pair: str,
        timeframe: str,
        since: Optional[pd.Timestamp],
        until: pd.Timestamp,
    ) -> None:
        """On-demand fetch from broker (D-04 mode b). Implementation delegates to scripts.update_cache."""
        from scripts.update_cache import fetch_range  # lazy import to avoid cycle
        fetched = fetch_range(pair, timeframe, since, until)
        if fetched is not None and len(fetched) > 0:
            self.upsert_bars(pair, timeframe, fetched, source="MT5")
```

**Why this shape:**
- The Title-case rename keeps **D-03 callers unchanged** — `df["Close"]` continues to work.
- The `is_pit_active()` check is **the answer to Area 3** — PitClock's `__enter__` increments `_PIT_DEPTH.depth`, `__exit__` decrements. PitClock needs a small augmentation (see "Pattern 3" below).
- `prepare_threshold=None` follows the [supabase pooler guidance](https://supabase.com/docs/guides/troubleshooting/supavisor-faq-YyP5tI).
- `executemany` + `ON CONFLICT DO NOTHING` matches D-04 mode and makes backfills idempotent.

### Pattern 2: PitClock instrumentation for `is_pit_active()` (Area 3)

**What:** Augment `V2/v3_intelligence/pit.py::PitClock` with a thread-local depth counter so `cache.is_pit_active()` can detect a clock on the call stack without API surface changes.

**When to use:** Phase 8.4 plan 02 — a small additive edit to PitClock; doesn't break Phase 8's contract.

```python
# Edits to V2/v3_intelligence/pit.py (additive only — no breaking changes)

import threading
_PIT_THREAD_DEPTH = threading.local()

def _bump(delta: int) -> None:
    cur = getattr(_PIT_THREAD_DEPTH, "depth", 0)
    _PIT_THREAD_DEPTH.depth = max(0, cur + delta)


def pit_active() -> bool:
    return getattr(_PIT_THREAD_DEPTH, "depth", 0) > 0


class PitClock:
    # ... existing code ...

    def __enter__(self) -> "PitClock":
        self._active = True
        if self._as_of is not None:   # UNBOUNDED stays inactive
            _bump(+1)
        return self

    def __exit__(self, *exc) -> None:
        self._active = False
        if self._as_of is not None:
            _bump(-1)
```

**Why thread-local:** Backtest is single-threaded today, but the live engine (Phase 10) and Phase 8.5's heatmap parallelisation (likely multiprocess via `joblib`) need per-thread isolation. Thread-local avoids cross-contamination at zero perf cost. UNBOUNDED stays out of the depth counter — that's the offline-fit sentinel, not a real clock.

Plan 03 must either change the default or pass `collection="trade_memory"` explicitly. **Recommend explicit pass** so existing callers (if any) aren't surprised.

### Pattern 4: Read-through CSV fallback (Area 4)

**What:** During Phase 8.4 transition window, `OHLCVCache.get_bars()` falls back to local CSV when Postgres returns empty AND the CSV exists.
**When to use:** Phase 8.4 plan 02 — keeps tests green during the migration; deletable in Phase 9 once cache is fully populated.

```python
# In OHLCVCache.get_bars(), at the end before raising / pulling:
if df.empty:
    csv_fallback = self._csv_fallback_path(pair, timeframe)
    if csv_fallback.exists():
        return _load_csv_titlecase(csv_fallback, start, end)

def _csv_fallback_path(self, pair: str, timeframe: str) -> Path:
    """Translate (pair, timeframe) to the canonical CSV name.

    Convention:
      Daily   → {PAIR}_DAILY_2015-2026.csv  (Phase 7 / 8 source-of-truth)
      H1      → {PAIR}_H1_4yr.csv  (Phase 7 / 8.4)
      H4      → {PAIR}_H4_4yr.csv  (Phase 8.4 D-08)
      M15     → {PAIR}_M15_60d.csv (Phase 7) — short window, known limitation
    """
    DATA = Path(__file__).resolve().parents[1] / "data"
    name = {
        "DAILY": f"{pair}_DAILY_2015-2026.csv",
        "H1":    f"{pair}_H1_4yr.csv",
        "H4":    f"{pair}_H4_4yr.csv",
        "M15":   f"{pair}_M15_60d.csv",
    }[timeframe]
    return DATA / name
```

This makes the migration safe: `pd.read_csv` callers can switch to `cache.get_bars(...)` one file at a time without breaking when the cache is empty.

### Anti-Patterns to Avoid

- **Auto-pulling inside PitClock:** silently leaks the future. The `is_pit_active()` check is mandatory — never make `_auto_pull` cleverly "pull only up to as_of" because that's still a feedback loop into the backtest's reality.
- **Per-pair branching for prices:** e.g., "JPY pairs use NUMERIC(8,3), others NUMERIC(10,5)". Single column type `NUMERIC(12,5)` covers both — JPY rates like 152.345 store fine; the leading-zero scale doesn't cost anything per-row.
- **supabase-py for SQL queries:** the [supabase-py guide](https://github.com/supabase/supabase-py) exists for REST/auth. Using it as a postgres client adds latency and constrains query shape.
- **Using `add` instead of `upsert` in ChromaDB backfill (D-14):** `add` raises on duplicate IDs — backfill re-runs would crash. `upsert` is idempotent ([Chroma docs](https://docs.trychroma.com/docs/collections/update-data)).
- **Hard-coding `PERIOD_H1` in the trade-replay indicator:** D-16 requires multi-timeframe rendering. Use `_Period` (the chart's period) and `iTime(_Symbol, _Period, shift)` instead.

## Common Pitfalls

### Pitfall 1: PgBouncer transaction mode breaks prepared statements
**What goes wrong:** Default `psycopg.connect(SUPABASE_DB_URL)` creates server-side prepared statements after the 5th identical query. PgBouncer in transaction mode (Supabase port 6543) routes each transaction to a different backend, so the prepared statement isn't there → `prepared statement "_pg3_0" does not exist` errors.
**Why it happens:** Pooler bug-by-design — transaction mode is incompatible with statement caching across requests.
**How to avoid:** Pass `prepare_threshold=None` to `psycopg.connect()`. Alternatively, use port 5432 (Session pooler) which keeps you on one backend per session.
**Warning signs:** `UndefinedObject` or `_pg3_X does not exist` errors on the 6th+ identical query.
*Sources:* [Supabase Supavisor FAQ](https://supabase.com/docs/guides/troubleshooting/supavisor-faq-YyP5tI), [GitHub issue 39227](https://github.com/supabase/supabase/issues/39227).

### Pitfall 2: Auto-pull inside PitClock leaks the future (Area 3)
**What goes wrong:** Backtest replay loop calls `cache.get_bars(pair, "H1", start, t)` for some replay-time `t`. If `t > cache.max_ts`, naive auto-pull fetches up to `now()` from the broker — including bars dated AFTER `t`. They land in cache. A subsequent read of `[start, t]` is OK, but the next backtest run sees cache that includes data fetched during a previous PiT replay → leakage corruption.
**Why it happens:** PiT and "fill cache from broker" are conflicting design goals when applied to the same timestamp.
**How to avoid:** `is_pit_active()` thread-local check (Pattern 2). When True, raise `FutureBarReadError` instead of auto-pulling — same exception PitClock already raises. Backtests that need historical data must pre-warm the cache via the manual `update_cache.py --since auto` CLI BEFORE entering PitClock.
**Warning signs:** Cache `max_ts` per (pair, tf) creeping forward during a PiT-marked backtest run; mysterious result drift between two runs of the same backtest on the same `as_of`.

### Pitfall 3: H4 data missing on IC Markets demo
**What goes wrong:** D-08 fetches H4 4yr for all 8 pairs. IC Markets' demo terminal "Max bars in history" defaults to 100,000 in MT5, but H4 over 4yr is only ~8,800 bars — well under the cap. However, `copy_rates_range` returns whatever the LOCAL terminal's history cache has, NOT what the broker has. If the operator hasn't scrolled the H4 chart back 4 years, MT5 hasn't downloaded those bars.
**Why it happens:** MT5 only fetches bars on demand to its local cache; `copy_rates_range` is a local-cache read, not a server query. Per the [MQL5 forum](https://www.mql5.com/en/forum/466803) and [QUANTREO blog](https://www.blog.quantreo.com/download-ticks-data/) — the H4 timeframe historically has had MT5-Python data inconsistencies on some brokers.
**How to avoid:** **Before running the H4 fetch script, manually scroll H4 charts to ~2022-04-01 in the MT5 GUI for each of 8 pairs, then run `copy_rates_range`.** Verify with Tools → Options → Charts → "Max bars in history" set to ≥ 50,000 (default 100,000 is fine). Alternative: open History Center (F2), Download button per pair × H4.
**Warning signs:** `copy_rates_range` returns a numpy array with `len(rates) < 1000` despite a 4yr range; the `WARN ... only N bars returned` line in `download_history.py` already covers this.

### Pitfall 4: ChromaDB doc_id collisions on backfill (Area 9)
**What goes wrong:** D-14 backfill embeds existing trades. RAGSignalFilter today builds doc_ids from `md5(symbol + entry_date + type)`. Two trades with the same triple — possible for high-frequency M15 scalps — collide → second `upsert` overwrites the first.
**Why it happens:** The hash key isn't unique enough.
**How to avoid:** Use `md5(symbol + entry_date.isoformat() + strategy + str(trade_id))` — the SQLite `id` column is unique by construction. For backfill from SQLite, the `id` is available; for backtest at trade-close time, generate a UUID4 if no SQLite id exists yet (the trade hasn't been written to SQLite yet at the moment of the on_trade_close call). Recommend: write to SQLite FIRST in `on_trade_close`, retrieve the `lastrowid`, then embed with `lastrowid` in the doc_id. This is what the current TradeLogger already returns from `INSERT` — but `log_trade` doesn't expose lastrowid; minor edit needed.
**Warning signs:** Backfill prints fewer "indexed" entries than rows in `marketmind.db.trades`; spot-check by counting `_col.count()` against `SELECT count(*) FROM trades`.

### Pitfall 5: MQL5 indicator chart-object orphans on timeframe switch (D-16)
**What goes wrong:** User has BandD_TradeReplay loaded on H1 chart, switches to H4. MT5 calls OnDeinit (reason `REASON_CHARTCHANGE`) then OnInit. If OnDeinit doesn't delete this indicator's objects, they remain on chart "owned" by the dead instance — orphans accumulate over operator session.
**Why it happens:** ObjectCreate doesn't auto-bind objects to the indicator's lifetime; chart-object lifetime is independent of indicator lifetime.
**How to avoid:** In OnDeinit, iterate `ObjectsTotal(0)` and `ObjectDelete(0, name)` for any object name with a known prefix (e.g., `"BandD_TR_"` for trade-replay objects). Use a unique prefix per indicator. Object deletion is asynchronous — per [MQL5 docs](https://www.mql5.com/en/forum/231702), the OnDeinit 2.5s budget is plenty for sub-thousand objects.
**Warning signs:** Chart accumulates duplicate/orphaned arrows after several timeframe switches.

### Pitfall 6: NUMERIC vs DOUBLE PRECISION write throughput
**What goes wrong:** `INSERT ... bars VALUES (...)` with NUMERIC columns is ~30% slower than DOUBLE PRECISION at scale. For a single-pass 35,000-bar backfill it's negligible (~1s); for repeated streaming inserts during live operation it's not.
**Why it happens:** NUMERIC is variable-length, encoded with overhead; DOUBLE PRECISION is fixed 8 bytes ([Postgres numeric types](https://www.postgresql.org/docs/current/datatype-numeric.html)).
**How to avoid:** For Phase 8.4 (read-heavy + bulk-insert), NUMERIC is correct ([Crunchy Data: Working with Money](https://www.crunchydata.com/blog/working-with-money-in-postgres)). For live tick ingestion in Phase 10 a separate `ticks` hot table could use DOUBLE PRECISION — out of scope here.
**Warning signs:** `executemany` of 35k rows takes >10s on a fast connection.

### Pitfall 7: mempalace `init` on existing repo overwrites mempalace.yaml
**What goes wrong:** Operator runs `mempalace init /path/to/helix` to "reconfigure" — the CLI re-detects rooms from folder structure and writes a fresh mempalace.yaml, clobbering the operator's keyword customisation.
**Why it happens:** `mempalace init` is non-idempotent for the YAML — it's a one-shot detection scaffold.
**How to avoid:** Run `mempalace init` ONCE; for subsequent re-mining use `mempalace mine` (which respects existing config). If keyword customisation is wanted, **edit mempalace.yaml AFTER init**, then never re-init. Better: skip `init` entirely if mempalace.yaml already exists, and write the desired keyword set directly.

//|  BandD_TradeReplay.mq5  — D-15, D-16, D-17                         |
//+------------------------------------------------------------------+
#property indicator_chart_window
#property indicator_buffers 0
#property indicator_plots   0

input color  InpShortColor = clrTomato;

void LoadAndRenderTrades()
{
    int handle = FileOpen(InpCsvPath, FILE_READ | FILE_CSV | FILE_ANSI, ',');
    if(handle == INVALID_HANDLE) { Print("CSV open fail: ", GetLastError()); return; }

        double   exit_px  = FileReadNumber(handle);
        double   sl       = FileReadNumber(handle);
        double   tp       = FileReadNumber(handle);

void RenderOne(int idx, datetime e_ts, datetime x_ts, double e_px, double x_px,
               double sl, double tp, string direction)
{
    bool is_long = (direction == "LONG");
    color side = is_long ? InpLongColor : InpShortColor;

    // Entry arrow — auto-anchors at chart's current period using iTime, no PERIOD_xx hardcoding
    string n_entry = OBJ_PREFIX + IntegerToString(idx) + "_entry";
    ObjectCreate(0, n_entry, OBJ_ARROW_BUY, 0, e_ts, e_px);
    ObjectSetInteger(0, n_entry, OBJPROP_COLOR, side);

    string n_exit = OBJ_PREFIX + IntegerToString(idx) + "_exit";
    ObjectCreate(0, n_exit, OBJ_ARROW_SELL, 0, x_ts, x_px);
    ObjectSetInteger(0, n_exit, OBJPROP_COLOR, side);

    // Connecting trendline
    string n_line = OBJ_PREFIX + IntegerToString(idx) + "_line";
    ObjectCreate(0, n_line, OBJ_TREND, 0, e_ts, e_px, x_ts, x_px);
    ObjectSetInteger(0, n_line, OBJPROP_COLOR, side);
    ObjectSetInteger(0, n_line, OBJPROP_RAY_RIGHT, false);

    // SL rectangle (entry_ts, sl) → (exit_ts, entry_px)
    string n_sl = OBJ_PREFIX + IntegerToString(idx) + "_sl";
    ObjectCreate(0, n_sl, OBJ_RECTANGLE, 0, e_ts, sl, x_ts, e_px);
    ObjectSetInteger(0, n_sl, OBJPROP_COLOR, InpSlColor);
    ObjectSetInteger(0, n_sl, OBJPROP_FILL, true);
    ObjectSetInteger(0, n_sl, OBJPROP_BACK, true);

    // TP rectangle (entry_ts, entry_px) → (exit_ts, tp)
    string n_tp = OBJ_PREFIX + IntegerToString(idx) + "_tp";
    ObjectCreate(0, n_tp, OBJ_RECTANGLE, 0, e_ts, e_px, x_ts, tp);
    ObjectSetInteger(0, n_tp, OBJPROP_COLOR, InpTpColor);
    ObjectSetInteger(0, n_tp, OBJPROP_FILL, true);
    ObjectSetInteger(0, n_tp, OBJPROP_BACK, true);

    // R-multiple text label at exit
    double risk = MathAbs(e_px - sl);
    double r_mult = (is_long ? (x_px - e_px) : (e_px - x_px)) / (risk > 0 ? risk : 1e-9);
    string n_txt = OBJ_PREFIX + IntegerToString(idx) + "_r";
    ObjectCreate(0, n_txt, OBJ_TEXT, 0, x_ts, x_px);
    ObjectSetString (0, n_txt, OBJPROP_TEXT, StringFormat("%.1fR", r_mult));
    ObjectSetInteger(0, n_txt, OBJPROP_COLOR, side);
    ObjectSetInteger(0, n_txt, OBJPROP_FONTSIZE, 9);
    ObjectSetInteger(0, n_txt, OBJPROP_ANCHOR, ANCHOR_LEFT);
}

### MQL5 ADR levels indicator (D-19)

```mql5
//+------------------------------------------------------------------+
//|  ADR_Levels.mq5  — D-18, D-19, D-16                              |
//+------------------------------------------------------------------+
#property indicator_chart_window
#property indicator_plots 0   // We draw via ObjectCreate, not buffers

input int InpLookbackDays = 20;
input color InpHighColor = clrDeepSkyBlue;
input color InpLowColor  = clrOrangeRed;
input color InpMidColor  = clrSilver;

const string OBJ_PREFIX = "ADR_LVL_";

int OnInit()  { Recompute(); EventSetTimer(60); return(INIT_SUCCEEDED); }
void OnDeinit(const int) { CleanupObjects(); EventKillTimer(); }
void OnTimer() { Recompute(); }
int OnCalculate(const int rates_total, const int prev_calculated, const datetime &time[],
                const double &open[], const double &high[], const double &low[],
                const double &close[], const long &tv[], const long &v[], const int &sp[])
{
    static datetime last_d1_bar = 0;
    datetime cur_d1 = iTime(_Symbol, PERIOD_D1, 0);
    if(cur_d1 != last_d1_bar) { Recompute(); last_d1_bar = cur_d1; }
    return(rates_total);
}

void Recompute()
{
    // ADR = mean of (Daily High - Daily Low) over InpLookbackDays
    double sum = 0;
    for(int i = 1; i <= InpLookbackDays; i++)
    {
        sum += iHigh(_Symbol, PERIOD_D1, i) - iLow(_Symbol, PERIOD_D1, i);
    }
    double adr = sum / InpLookbackDays;

    double today_open = iOpen(_Symbol, PERIOD_D1, 0);
    double hi  = today_open + adr / 2.0;
    double lo  = today_open - adr / 2.0;
    double mid = today_open;

    DrawHLine(OBJ_PREFIX + "high", hi, InpHighColor);
    DrawHLine(OBJ_PREFIX + "low",  lo, InpLowColor);
    DrawHLine(OBJ_PREFIX + "mid",  mid, InpMidColor);
}

void DrawHLine(string name, double price, color c)
{
    if(ObjectFind(0, name) < 0) ObjectCreate(0, name, OBJ_HLINE, 0, 0, price);
    ObjectSetDouble(0, name, OBJPROP_PRICE, price);
    ObjectSetInteger(0, name, OBJPROP_COLOR, c);
    ObjectSetInteger(0, name, OBJPROP_STYLE, STYLE_DASH);
    ObjectSetInteger(0, name, OBJPROP_BACK, true);
}

void CleanupObjects()
{
    for(int i = ObjectsTotal(0) - 1; i >= 0; i--)
    {
        string n = ObjectName(0, i);
        if(StringFind(n, OBJ_PREFIX) == 0) ObjectDelete(0, n);
    }
}
```

|--------------|------------------|--------------|--------|
